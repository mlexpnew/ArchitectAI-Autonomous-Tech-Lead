# ArchitectAI API & Interface Documentation

This document covers both the **ArchitectAI Orchestration API** (how to run and invoke ArchitectAI programmatically and via CLI) and the **Generated Application API Standards** (the specifications followed by projects generated by ArchitectAI).

---

## 1. ArchitectAI Orchestration API

### 1.1 Command-Line Interface (CLI)

ArchitectAI provides a unified CLI entry point via `architectai.py`:

```bash
python3 architectai.py generate \
  --name "Hospital Management System" \
  --requirements "requirements.txt" \
  --output "outputs/Hospital_Management_System"
```

#### CLI Arguments
| Flag | Required | Type | Description |
| :--- | :--- | :--- | :--- |
| `--name` | Yes | string | Human-readable name of the project to generate |
| `--requirements`| Yes | file path | Path to text file containing natural-language requirements |
| `--output` | Yes | directory path | Target folder where generated project and reports will be saved |

---

### 1.2 Programmatic Python API

You can embed ArchitectAI into your own scripts or CI/CD pipelines:

```python
from orchestration.architect_pipeline import ArchitectPipeline

# 1. Initialize the pipeline with target output directory
pipeline = ArchitectPipeline(
    output_dir="generated_projects/Inventory_Service"
)

requirements = """
Build an Inventory Management System with Product, Category, and WarehouseStock.
A Category has many Products.
Each Product can have WarehouseStock records across multiple Warehouses.
"""

# 2. Execute end-to-end generation, validation, and packaging
result = pipeline.generate(
    requirements=requirements,
    project_name="Inventory Management System"
)

# 3. Access execution artifacts and validation state
print("Blueprint Entities:", [e.name for e in result["blueprint"].entities])
print("Validation Status:", result["validation"]["valid"])
print("Generated Artifacts:", len(result["artifacts"]))
print("Zip Archive:", result["export"]["archive"])
```

#### Pipeline Result Dictionary

## 2. Generated Application API Standards

Projects generated by ArchitectAI follow strict REST and OpenAPI standards.

### 2.1 Standard Application Endpoints
Every generated backend includes:
- **`GET /docs`**: Interactive Swagger UI documentation.
- **`GET /redoc`**: ReDoc alternative API documentation.
- **`GET /openapi.json`**: OpenAPI 3.1 specification schema.
- **`GET /health`**: Health status probe.
  ```json
  { "status": "healthy", "version": "1.0.0" }
  ```

### 2.2 Standard RESTful Resource Operations
For each entity generated (e.g., `Patient`), the following standard endpoints are exposed:

| HTTP Method | Route | Description | Success Status |
| :--- | :--- | :--- | :--- |
| `POST` | `/api/v1/{entities}/` | Create a new entity instance | `201 Created` |
| `GET` | `/api/v1/{entities}/` | List paginated entities | `200 OK` |
| `GET` | `/api/v1/{entities}/{id}` | Retrieve entity by ID | `200 OK` |
| `PUT` | `/api/v1/{entities}/{id}` | Full update of entity | `200 OK` |
| `DELETE` | `/api/v1/{entities}/{id}` | Delete entity by ID | `200 OK` or `204 No Content` |

### 2.3 Error Response Standard
All 4xx and 5xx responses conform to a unified error model:
```json
{
  "detail": [
    {
      "loc": ["body", "email"],
      "msg": "value is not a valid email address",
      "type": "value_error.email"
    }
  ]
}
```
